# Видеочат-комната

Комната на **4 участника**: видео и звук через WebRTC mesh (медиа идёт напрямую между
браузерами), текстовый чат и список участников — через Socket.io. Регистрации нет: участник
вводит имя, создаёт комнату и делится ссылкой.

Монорепозиторий на npm workspaces: `shared` (общие константы, словарь событий и валидация),
`server` (Express + Socket.io) и `client` (React + Vite). Язык — JavaScript (ES6+, ESM),
TypeScript не используется; формы данных описаны JSDoc-комментариями.

Документы проекта: [PRD](./prd-video-chat-room.md),
[дизайн](./prds/video-chat-room/design-video-chat-room.md),
[план работ](./prds/video-chat-room/impl-video-chat-room.md).

## Демо

**Видео: [ССЫЛКА_НА_ВИДЕО](https://drive.google.com/file/d/1cXVU3VFsw0Vu024FSgxbtm0JkZaHv1iR/view?usp=sharing)**

Что показано: создание комнаты и вход по ссылке-приглашению, звонок вчетвером в сетке 2×2,
общий чат с системными сообщениями, выключение микрофона и камеры с индикаторами у собеседников,
отказ пятому участнику и выход из комнаты.

## Требования

- **Node.js ≥ 20.9** (версия для `nvm` — в [`.nvmrc`](./.nvmrc)), npm 10+.
- Браузер: **Chrome, Firefox или Edge 100+**. Safari не поддерживается.
- **HTTPS или `localhost`.** `getUserMedia` и WebRTC работают только в защищённом контексте,
  поэтому по `http://<IP-в-LAN>` камера и микрофон недоступны — см.
  [HTTPS в локальной сети](#https-в-локальной-сети-mkcert).

## Быстрый старт

```bash
npm install          # из корня: ставит зависимости всех workspace-пакетов
npm run dev          # сервер :3000 + Vite :5173
```

Откройте `https://localhost:5173` (без сертификатов — `http://localhost:5173`; на `localhost`
браузер тоже даёт доступ к устройствам). Вторую вкладку откройте по ссылке из кнопки
«Скопировать ссылку»: каждая вкладка — независимый участник.

Прод-подобный запуск одним процессом, как для демо в локальной сети:

```bash
npm run build        # сборка клиента в client/dist
npm start            # один процесс на :3000 отдаёт статику и обслуживает сигналинг
```

## Скрипты

| Команда                    | Что делает                                                           |
| -------------------------- | -------------------------------------------------------------------- |
| `npm run dev`              | Сервер с `--watch` на `:3000` и Vite на `:5173` с proxy `/socket.io` |
| `npm run build`            | Сборка клиента в `client/dist`                                       |
| `npm start`                | Прод-подобный запуск: один процесс раздаёт `client/dist` и сигналинг |
| `npm run lint`             | ESLint по всему репозиторию                                          |
| `npm run format`           | Prettier с записью; `npm run format:check` — только проверка         |
| `npm test`                 | Unit- и компонентные тесты (Vitest)                                  |
| `npm run test:coverage`    | То же с покрытием и порогами                                         |
| `npm run test:integration` | Интеграционные тесты сервера на настоящих сокетах                    |
| `npm run test:e2e`         | Playwright: собирает клиент, поднимает сервер и гоняет сценарии      |

Перед первым `npm run test:e2e` установите браузер: `npx playwright install chromium`.

Нагрузочный прогон сигналинга (50 комнат × 4 сокета) запускается отдельно и в CI не входит:

```bash
node scripts/load-signaling.js
```

Методика и результаты последнего прогона — в [docs/load-test.md](./docs/load-test.md).

## Структура монорепозитория

```text
/
├─ shared/src/      # @vcr/shared: константы, имена событий, коды ошибок, валидация
├─ server/src/      # Express + Socket.io: config, http/app.js, rooms/, socket/
├─ server/test/     # интеграционные тесты на настоящих сокетах
├─ client/src/      # React: pages/, components/, services/, state/, hooks/, utils/
├─ e2e/             # Playwright-сценарии
├─ scripts/         # load-signaling.js — нагрузочный прогон
├─ docs/            # отчёты: нагрузка, ручная приёмка
└─ certs/           # сертификаты mkcert для LAN (в .gitignore)
```

Комнаты, участники и история чата живут **в памяти сервера**: базы данных нет, перезапуск
процесса очищает всё.

## HTTPS в локальной сети (mkcert)

Для демо с нескольких устройств нужен сертификат на IP-адрес хоста: без HTTPS браузер не даст
доступ к камере и микрофону нигде, кроме `localhost`.

**1. Установите mkcert**

```bash
# Windows (choco или scoop)
choco install mkcert
# scoop bucket add extras; scoop install mkcert

# macOS (nss нужен для Firefox)
brew install mkcert nss

# Linux (Debian/Ubuntu)
sudo apt install libnss3-tools
# затем бинарник mkcert из релизов проекта: https://github.com/FiloSottile/mkcert/releases
```

**2. Создайте локальный CA и сертификат** — укажите все адреса, по которым будете открывать
приложение, включая IP-адрес хоста в сети:

```bash
mkcert -install
mkcert -cert-file certs/cert.pem -key-file certs/key.pem localhost 127.0.0.1 ::1 192.168.1.50
```

`192.168.1.50` замените на свой адрес: `ipconfig` (Windows) или `ip addr` / `ifconfig` (macOS,
Linux). Каталог `certs/` в `.gitignore` — сертификаты в репозиторий не попадают.

**3. Запустите с сертификатами**

```bash
# bash / zsh
SSL_CERT_PATH=certs/cert.pem SSL_KEY_PATH=certs/key.pem npm start
```

```powershell
# PowerShell
$env:SSL_CERT_PATH = "certs/cert.pem"; $env:SSL_KEY_PATH = "certs/key.pem"; npm start
```

Приложение открывается по `https://192.168.1.50:3000`. В dev-режиме сертификаты подхватывает
Vite: если файлы `certs/cert.pem` и `certs/key.pem` существуют, `npm run dev` поднимает
`https://<IP>:5173` сам.

**4. Доверьте корневой CA на других устройствах.** Сертификат mkcert подписан локальным CA,
которого нет на телефонах и ноутбуках коллег:

```bash
mkcert -CAROOT        # путь к rootCA.pem
```

Скопируйте `rootCA.pem` на устройство и импортируйте:

- **Windows:** двойной клик → «Установить сертификат» → «Локальный компьютер» → «Доверенные
  корневые центры сертификации».
- **macOS:** Keychain Access → System → перетащить файл → в свойствах выбрать «Always Trust».
- **Android:** Настройки → Безопасность → Шифрование → Установить сертификат → CA.
- **iOS:** установить профиль, затем включить доверие в «Основные → Об этом устройстве →
  Доверие сертификатам».

Без импорта останется принять предупреждение браузера вручную — после этого `getUserMedia`
работает, но на демо это выглядит плохо и на iOS срабатывает не всегда.

**Запасной вариант — не для демо.** Если сертификат сделать не получается, Chrome можно запустить
с флагом, который считает конкретный HTTP-адрес защищённым:

```bash
chrome --unsafely-treat-insecure-origin-as-secure=http://192.168.1.50:3000 --user-data-dir=/tmp/vcr-insecure
```

Флаг нужен на **каждом** устройстве, ослабляет защиту браузера и не работает в Firefox и Safari.
Годится только для отладки в одиночку.

## Переменные окружения

Все — у сервера; клиент настроек не требует.

| Переменная                       | По умолчанию                   | Назначение                                                     |
| -------------------------------- | ------------------------------ | -------------------------------------------------------------- |
| `PORT`                           | `3000`                         | Порт сервера                                                   |
| `HOST`                           | `0.0.0.0`                      | Интерфейсы прослушивания; `0.0.0.0` — доступен в сети          |
| `SSL_CERT_PATH` / `SSL_KEY_PATH` | —                              | Заданы оба — HTTPS; иначе HTTP (пригоден только к `localhost`) |
| `STUN_URLS`                      | `stun:stun.l.google.com:19302` | Список через запятую; передаётся клиенту при входе в комнату   |
| `CHAT_HISTORY_LIMIT`             | `200`                          | Сообщений в истории одной комнаты                              |
| `LOG_LEVEL`                      | `info`                         | Уровень pino: `fatal`…`trace` или `silent`                     |
| `CLIENT_DIST_DIR`                | `client/dist`                  | Каталог собранного клиента                                     |

Лимит в 4 участника через окружение не настраивается: он завязан на топологию mesh (при
5 участниках каждый клиент кодировал бы 4 исходящих потока).

Проверка живости: `GET /healthz` отдаёт `{"status":"ok","rooms":…,"participants":…,"uptimeSec":…,"version":…}`.

## Ограничения

- **Один процесс.** Лимит «не более 4» держится на том, что вход в комнату выполняется
  синхронно в одном процессе. Запуск в `cluster` или за несколькими репликами сломает инвариант:
  состояние комнат у каждого процесса своё.
- **Нет TURN.** ICE использует только публичный STUN, поэтому пара может не соединиться при
  строгом NAT или при изоляции клиентов в Wi-Fi — участник увидит бейдж «Нет медиасоединения».
- **Данные в памяти.** Перезапуск удаляет комнаты, участников и историю чата; на клиенте между
  перезагрузками ничего не сохраняется, имя спрашивается заново.
- **Только 4 участника** и один размер сетки; мобильная вёрстка не нормируется, макет
  рассчитан на ширину от 1024px.
- Нет записи звонка, демонстрации экрана, реакций и активного говорящего — это вне scope PRD.

## Диагностика

**Участники видят друг друга в списке, но видео нет.** Значит сигналинг работает, а P2P — нет.
Откройте `chrome://webrtc-internals` на обеих сторонах и посмотрите на `iceConnectionState`
и на кандидатов в `candidate-pair`:

- кандидатов `host` вообще нет → камера и микрофон не захвачены, ищите ошибку выше;
- кандидаты есть, но пара не выбрана → трафик между устройствами не проходит.

Типичные причины непроходимости в офисной сети:

- **Изоляция клиентов в Wi-Fi** (AP isolation, «гостевая сеть»): устройства видят роутер,
  но не друг друга. Проверяется `ping` между устройствами; лечится другой точкой доступа
  или проводом.
- **Заблокированный mDNS.** Chrome прячет локальные IP за `.local`-кандидатами; если mDNS
  в сети запрещён, они бесполезны.
- **Файрвол хоста** блокирует входящие UDP-порты Node или браузера.

**Браузер не спрашивает разрешение на камеру.** Адрес открыт по HTTP и это не `localhost`:
защищённого контекста нет. Поднимите HTTPS по инструкции выше.

**«Сервер недоступен».** Проверьте `GET /healthz` и то, что клиент открыт с того же хоста
и порта, что и сервер: CSP разрешает соединения только с ним (`connect-src 'self'`).

**Звука нет, пока не кликнешь.** Политика autoplay: приложение показывает баннер «Включить
звук», нажатие снимает блокировку.
