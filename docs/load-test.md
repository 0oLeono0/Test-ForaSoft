# Нагрузочный прогон сигналинга

Лёгкая проверка сервера под нагрузкой из TDD §11.5. Полноценный нагрузочный тест медиа не нужен:
медиа идёт P2P, через сервер проходят только сигналинг и чат.

## Что делает прогон

`node scripts/load-signaling.js` поднимает сервер отдельным процессом (fork того же файла в роли
`server`, порт эфемерный) и нагружает его из процесса-родителя:

- **50 комнат по 4 участника** — 200 сокетов `socket.io-client` с браузерными параметрами
  (TDD §6.2); четыре входа в одну комнату уходят одновременно, поэтому заодно проверяется
  атомарность лимита (FR-7).
- **30 фиктивных `signal` на участника** — по кругу трём пирам, каждый десятый с SDP ~4 КБ,
  остальные ICE-кандидаты.
- **20 сообщений чата на участника** с паузой 1100 мс: rate limit чата — 5 сообщений за 5 с
  (TDD §10.4), то есть в среднем одно в секунду, и прогон измеряет доставку, а не работу лимита.

Объёмы меняются флагами: `--rooms`, `--participants`, `--messages`, `--signals`.

## Как считаются метрики

| Метрика             | Источник                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------- |
| Лишние `ROOM_FULL`  | Коды ошибок в ack `room:join`. В комнате ровно 4 участника, поэтому любой `ROOM_FULL` — лишний |
| p95 доставки чата   | `performance.now()` между `chat:send` у автора и `chat:message` у каждого из трёх получателей  |
| RSS сервера         | `process.memoryUsage()` в процессе сервера, опрос по IPC каждые 500 мс; берётся пик            |
| Комнаты и участники | `GET /healthz` под нагрузкой и после выхода всех участников                                    |

RSS снимается в процессе сервера, а не в процессе нагрузки: две сотни клиентских сокетов живут
у родителя и в измерение не попадают. В `/healthz` поля с памятью нет — контракт ответа
зафиксирован в TDD §6.1 и здесь не расширялся.

Скрипт печатает таблицу результатов сразу в Markdown и завершается кодом 1, если хотя бы один
критерий не выполнен.

## Результат прогона

**Дата:** 2026-09-18. **Окружение:** AMD Ryzen 5 2600 (12 логических ядер), 16 ГБ ОЗУ,
Windows 10 19045, Node v24.12.0, сервер `0.1.0`, localhost.

Команда: `node scripts/load-signaling.js` (значения по умолчанию: 50 × 4, 30 сигналов,
20 сообщений).

| Проверка                          | Получено                  | Ожидалось                 | Итог |
| --------------------------------- | ------------------------- | ------------------------- | ---- |
| Лишних ROOM_FULL нет              | 0                         | 0                         | ок   |
| Ошибок входа нет                  | нет                       | нет                       | ок   |
| Ошибок чата нет                   | нет                       | нет                       | ок   |
| Ошибок сигналинга нет             | нет                       | нет                       | ок   |
| Сигналы доставлены                | 6000                      | 6000                      | ок   |
| Сообщения доставлены всем         | 12000                     | 12000                     | ок   |
| Комнаты под нагрузкой             | 50 комнат, 200 участников | 50 комнат, 200 участников | ок   |
| Комнаты освободились после выхода | 0 комнат                  | 0 комнат                  | ок   |
| p95 доставки чата                 | 26.4 мс                   | < 50 мс                   | ок   |
| Пиковый RSS сервера               | 91.5 МБ                   | < 150.0 МБ                | ок   |

Задержка чата, мс: p50 15.5, p95 26.4, p99 29.5, max 35.6 (12 000 замеров).
RSS сервера: старт 60.8 МБ, пик 91.5 МБ, после нагрузки 71.4 МБ.

**Вывод:** критерии §11.5 выполнены. Все 6000 сигналов и 12 000 доставок чата прошли без
`signal:error` и без `RATE_LIMITED`; после выхода участников комнаты удалены (`rooms: 0`), а RSS
вернулся к 71.4 МБ — заметной утечки на 200 сокетах не видно.

## Оговорки

- Прогон на localhost: сетевая задержка в p95 не входит, в LAN к ней добавится RTT.
- Нагрузка создаётся из одного процесса Node, поэтому её собственные 200 сокетов конкурируют
  за CPU с сервером. Это ухудшает измеренную задержку, но не улучшает её: запас относительно
  порога в 50 мс реальный.
- Прогон не входит в `npm test` и в CI: он занимает около 40 секунд и чувствителен к загрузке
  машины. Запускается вручную перед сдачей и после изменений в сигналинге или в лимитах.
